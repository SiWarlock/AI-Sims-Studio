# /tdd brief — provider_test_call

## Feature
The §18(1) **per-provider test-call**: the onboarding API-key flow validates a keychain-written provider key by
issuing the read/connectivity probe `POST /settings/providers/{p}/test → TestProviderResponse`, and interprets the
result into a UI-facing pass/fail (latency on success; a `parseErrorCode`-normalized error code + message on
failure). The visual API-key entry screen is **design-fixture (D4), NOT this slice**.

## Use case + traceability
- **Task ID:** 7.2
- **Architecture sections it implements:** `ARCHITECTURE.md §18` (onboarding prereq #1 — provider/LLM API-key entry
  with per-provider **test-call** validation) + `ARCHITECTURE.md §4` (the `POST /settings/providers/{p}/test` IPC
  command + its `TestProviderResponse`).
- **Related context:**
  - Contract surface present in `packages/contracts/generated/contracts.ts`: `TestProviderRequest { model?: string |
    null }`, `TestProviderResponse { ok: boolean; latencyMs?: number | null; error?: ErrorEnvelope | null }` (the
    `error` carries the 0.2 `ErrorEnvelope` on failure). The endpoint `POST /settings/providers/{p}/test` is **already
    in** `src/ipc/endpoints.ts` (mutating) and the frozen snapshot — **no catalog change needed**.
  - `parseErrorCode` (`packages/contracts/generated/helpers`, Lesson 13 upstream) maps an unknown `error.code` →
    `SYSTEM` — already used by `src/ipc/sse-schema.ts` (carry-forward 0.2/D10b). Reuse it here for the failure path.
  - Mirrors the readiness-gate slice (7.2) structure: a named client method + a pure interpretation function + a
    composed controller, all tested over a mock `IpcClient`; the React screen is a thin design-fixture consumer.
  - The key being validated was written to the OS keychain by 7.2b-1 (`src/keychain/provider-keys.ts`,
    `sanitizeProviderId` / `PROVIDER_ID_RE`); secrets never ride the request body (rule-5) — the sidecar reads the
    key from the keychain (7.2b-2).

## Acceptance criteria (what "done" means)
- [ ] `IpcClient` gains `testProvider(providerId: string, body?: TestProviderRequest): Promise<TestProviderResponse>`
      issuing `POST /settings/providers/{p}/test` with the `{p}` path param substituted to `providerId`, the token
      header, AND an `Idempotency-Key` (mutating endpoint, per the existing `buildRequestHeaders`). **No secret in the
      body** (rule-5 — the optional `model` is the only body field).
- [ ] `interpretProviderTest(resp: TestProviderResponse): ProviderTestResult` is a pure function:
  - `ok:true` → `{ valid: true, latencyMs }` (latency surfaced when present).
  - `ok:false` with an `error` → `{ valid: false, code: parseErrorCode(error.code), message: error.creatorMessage }`
    (`ErrorEnvelope` fields are `creatorMessage` (user-facing, rule-5-safe) + `maintainerDetail` — surface
    `creatorMessage`, NEVER `maintainerDetail`).
  - `ok:false` with a **missing/null `error`** → `{ valid: false, code: "SYSTEM", message: <generic> }` (defensive —
    a failed probe must always yield an actionable, value-free code; see Step-2.5 Q3).
  - an **unknown** `error.code` → `code: "SYSTEM"` via `parseErrorCode` (additive-enum tolerance).
- [ ] `testProviderConnectivity(client, providerId, body?)` composes `client.testProvider(...)` →
      `interpretProviderTest(resp)` — the production entry point the API-key flow invokes.
- [ ] All unit tests in `test/ipc/client.test.ts` + `test/onboarding/provider-test.test.ts` pass.
- [ ] `/preflight` clean (`pnpm lint && pnpm typecheck && pnpm test:run`).
- [ ] No cross-doc invariant change (consume-only — see below).

## Wiring / entry point (Step 7.5)
The production entry point is **`testProviderConnectivity(client, providerId)`** — invoked by the onboarding API-key
entry flow after a key is written (7.2b-1), to validate it before continuing. Reachable via the wired `createIpcClient`
(`src/bootstrap.ts` / `src/renderer-entry.ts`). **The visual API-key entry screen** (the input + the inline
valid/invalid + latency/remediation surface) is a thin design-fixture (D4) consumer, **not `/tdd`** — mapped
`not-tested-because: visual/wiring`. See Step-2.5 Q5 for thin-view depth this slice vs. the screen slice; if `/wired`
shows the controller test-only, route it as a Future TODO (last-consumer = the API-key screen slice), same as the
readiness-gate controller (ledger T16).

## RED test outline (Step 2)

`test/ipc/client.test.ts`:
1. **`test_test_provider_is_mutating_post_with_idempotency_key`** — `testProvider("openai")` issues `POST
   /settings/providers/openai/test`.
   - Asserts: method `POST`, the `{p}` param substituted to `openai`, `X-AISims-Token` present, `Idempotency-Key`
     present (mutating). Why: `§4` mutating-command idempotency (Lesson 5).
2. **`test_test_provider_no_secret_in_body`** — only `model` (when given) rides the body; no key field.
   - Asserts: body has no secret/apiKey field. Why: rule-5 (secrets are keychain-only, never on the wire body).
3. **`test_test_provider_returns_parsed_response`** — resolves the JSON to `TestProviderResponse`.
   - Asserts: body round-trips to `{ ok, latencyMs?, error? }`. Why: `§4` response contract.

`test/onboarding/provider-test.test.ts`:
4. **`test_interpret_ok_true_surfaces_latency`** — `{ok:true, latencyMs:42}` → `{valid:true, latencyMs:42}`.
   - Why: `§18` success path (latency is the surfaced signal).
5. **`test_interpret_ok_false_maps_known_error_code`** — `{ok:false, error:{code:"PROVIDER_AUTH_QUOTA",...}}` →
   `{valid:false, code:"PROVIDER_AUTH_QUOTA", message:<env.creatorMessage>}`.
   - Why: `§18` actionable failure; the recognized code is preserved.
6. **`test_interpret_ok_false_unknown_code_to_system`** — an off-contract `error.code` → `code:"SYSTEM"` via
   `parseErrorCode`.
   - Why: additive-enum tolerance (0.2/D10b) — an unrecognized code never crashes the flow.
7. **`test_interpret_ok_false_missing_error_defaults_system`** — `{ok:false, error:null}` → `{valid:false,
   code:"SYSTEM", ...}`.
   - Why: defensive — a failed probe with no envelope still yields an actionable, value-free code (Step-2.5 Q3).
8. **`test_interpret_preserves_error_message`** — the `ErrorEnvelope.creatorMessage` is surfaced on failure.
   - Why: `§18` remediation messaging (`creatorMessage` is the user-facing, rule-5-safe field).
9. **`test_test_provider_connectivity_composes_client_then_interpret`** — `testProviderConnectivity(mockClient,
   "openai")` awaits `testProvider` then returns `interpretProviderTest(resp)`.
   - Why: the Step-7.5 entry point; pins the composition over a mock `IpcClient`.

*(Step-2.5 Q1, conditional)* **`test_test_provider_connectivity_rejects_malformed_provider_id`** — a malformed
providerId is rejected before the call fires (if the validate-first default is taken).

## Things to flag at Step 2.5
1. **Validate `providerId` before the call?** Reuse `sanitizeProviderId`/`PROVIDER_ID_RE` (7.2b-1) so the probe never
   fires on a malformed id, vs. rely on the client's `encodeURIComponent`. My default vote: **validate via the
   existing `sanitizeProviderId`** (fail-safe + consistent with the keychain client; the id is the same contract). If
   this becomes a third consumer of `PROVIDER_ID_RE`, extract a shared validator (resolves ledger T14).
2. **`ProviderTestResult` shape.** A discriminated union `{valid:true, latencyMs?}` | `{valid:false, code, message?}`.
   My default vote: **discriminated union** (the UI renders two distinct states; a flat shape invites invalid combos).
3. **`ok:false` with missing `error`.** My default vote: **default to `code:"SYSTEM"` + a generic message** — a failed
   probe must always be actionable and value-free.
4. **Zod-validate the response or cast?** My default vote: **cast** (match the existing REST client + readiness-gate
   Q5); the interpretation function is the defensive boundary and `parseErrorCode` already tolerates an unknown code.
5. **Controller wiring depth this slice.** My default vote: **land `testProviderConnectivity` as the tested entry
   point now**; the visual API-key screen rides 7.3/onboarding design-fixture (D4). If `/wired` shows it test-only,
   route a Future TODO (last-consumer = the API-key screen slice), mirroring ledger T16.
