# /tdd brief — readiness_gate

## Feature
The §18(4) **system-readiness gate**: a deterministic decision over the merged read-only `GET /readiness →
ReadinessReport` that computes whether "New Project" may start (blocked if any subsystem is blocked; "not yet
determined" when no checks have run), plus the token-bearing client call that fetches the report. The visual gate
screen (button-disable + remediation list) is **design-fixture (D4), NOT this slice**.

## Wiring / entry point (Step 7.5)

path via the IPC client (`createIpcClient`) already wired in `src/bootstrap.ts` / `src/renderer-entry.ts`. **The
visual gate screen** (disable the New-Project button + render the remediation list) is a thin view that **rides
design-fixture review (D4), not `/tdd`** — mapped `not-tested-because: visual/wiring`. See Step-2.5 Q6 for how deep

## Things to flag at Step 2.5
1. **canStart rule — fail-safe allow-list vs. deny-list.** "No check is `blocked`" (deny-list) vs. "every check ∈
   `{ready,degraded}`" (allow-list). My default vote: **allow-list** — it fails closed on an off-contract/garbage
   status (test 11) while still blocking on `blocked`. Minor cost: one extra test.
2. **Does `degraded` block New Project?** My default vote: **No — allow with a surfaced non-blocking warning**
   (`degraded` = impaired, not missing; matches "blocked if any subsystem blocked").
3. **Trust `report.overall` or recompute from `checks`?** My default vote: **recompute from `checks`** — the gate owns
   its own decision; `overall` is advisory/display. Empty-checks handling needs per-check inspection anyway. Pinned by
   test 9.
4. **Empty `checks` → which state?** My default vote: **`indeterminate`, `canStartNewProject:false`** ("not yet
   determined") — never optimistic-ready.
5. **Zod-validate the `GET /readiness` REST response, or cast like the existing client?** The current REST client
   casts (`getSettings`/`listProjects` use `as T`); only the SSE path Zod-validates (Lesson 2). My default vote:
   **match the existing REST client (cast)** — the gate logic is the defensive boundary (empty-checks + allow-list);
   adding Zod only here would be an inconsistent one-off. A REST-wide Zod boundary is its own cross-cutting slice if
   we ever want it.
6. **How deep does the controller wire in THIS slice?** My default vote: **land `evaluateNewProjectReadiness` as the
   tested entry point now** (reachable via the existing `createIpcClient` wiring); the visual gate screen + its
   button-disable/remediation rendering ride **7.3 design-fixture (D4)**. If genuine `/wired` reachability needs a
   minimal thin-view consumer this slice, add one (visuals = design-fixture, mapped `not-tested-because:
   visual/wiring`) rather than leaving the controller test-only.
