# /tdd brief — electron_shell_sse_observer_reconnect

## Feature
The desktop UI's foundational **thin observer**: an Electron shell that mints/hands over the per-launch
loopback token (parent→child channel), a token-bearing IPC client + fetch-based SSE subscription that
parses the frozen §4 event taxonomy through a Zod runtime boundary, `Last-Event-ID` reconnect-replay with
idempotent re-apply, a pure server-driven state projection that holds **no durable pipeline authority**, and
the **§21 UI-responsiveness contract test** (a slow mock stage must not block command-ack or the SSE
heartbeat). This is the load-bearing base every Phase-7 screen (7.3) renders on.

## Acceptance criteria (what "done" means)
- [ ] **Token on every request.** The IPC client attaches `X-AISims-Token` on every REST call and the SSE
      subscription presents it too; constructing/using a client **without** a token is impossible (throws at
      construction). The token is never logged, persisted, or placed in a URL/query string (forbidden pattern 3).
- [ ] **Idempotency-Key on mutating commands only.** Every endpoint in `MUTATING_ENDPOINTS` (all but
      `GET /projects`) carries an `Idempotency-Key` header; the one read-only endpoint omits it.
- [ ] **SSE Zod boundary parses the frozen taxonomy.** Each SSE frame is validated into the typed discriminated
      union keyed on the `event` tag (`progress`/`step-state`/`log`/`validation`/`cost`/`gate-needed`/`done`/
      `error`); a frame with an unknown `event` tag or a malformed payload is rejected at the boundary (never
      silently coerced). The Zod schema's inferred type is **type-equal to the generated `SseEvent` members**
      (compile-time parity guard, see RED #9) — the schema validates at runtime; the **type** comes from the
      generated contract.
- [ ] **ErrorEnvelope `code` tolerance.** An `error` event whose `error.code` is not a known `ErrorCode`
      degrades to `SYSTEM` via `parseErrorCode` (carry-forward 0.2/D10b); all other fields validate strictly.
- [ ] **Last-Event-ID reconnect-replay.** The observer tracks the last seen event `id`; on reconnect it sends
      `Last-Event-ID: <last-id>` so the server replays; replayed events with `id ≤ lastEventId` are dropped
      (no double-processing).
- [ ] **Idempotent projection.** The state projection is a pure reducer over the event stream; applying the
      same event (same `id`) twice is a no-op, and the read-model is fully rebuildable from a replayed stream —
      it holds **no durable pipeline authority** (forbidden pattern 2).
- [ ] **§21 UI-responsiveness gate.** Against a mock sidecar where one stage is deliberately slow:
      `client.startRun(...)` resolves promptly (command-ack is not blocked by the slow stage) **and** the SSE
      heartbeat + unrelated events keep arriving while the slow stage is pending (the observer never blocks the
      stream on one stage).
- [ ] **Loopback token handoff.** The Electron main obtains the per-launch token and hands it to the renderer
      over the preload `contextBridge` (trusted parent→child channel, §4/§16); the handoff helper is unit-tested
      and guarantees the token is exposed to the renderer **only** (not to `window`/global, not to any log sink).
- [ ] All unit tests in `apps/desktop/test/` pass; `/preflight` clean (`pnpm lint && pnpm typecheck && pnpm test:run`).

## Wiring / entry point (Step 7.5)
**Production entry = `apps/desktop/electron/main.ts`** → on `app.whenReady()`: obtain the loopback token →
create the `BrowserWindow` with the preload → the preload bridges the token into the renderer. **Renderer
bootstrap = `apps/desktop/src/bootstrap.ts:bootstrapObserver(token, baseUrl)`** — constructs the IPC client,
opens the SSE subscription, and feeds events into the projection. The shell loads a **static placeholder
renderer** (no React yet — see Step-2.5 Q2); the visible screens that read the projection land in **7.3**.
Confirm `bootstrapObserver` is invoked from the loaded renderer, not only from tests (`/wired bootstrapObserver`).

## RED test outline (Step 2)
Tests in `apps/desktop/test/`:

1. **`test_client_attaches_token_on_every_request`** — Asserts: a `fetchImpl` spy sees `X-AISims-Token` on REST calls. Why: §4/§16 per-launch token; forbidden pattern 3.
2. **`test_client_without_token_throws`** — Asserts: `createIpcClient` with no/empty token throws (can't construct an unauthenticated client). Why: forbidden pattern 3 (no untokened request path exists).
3. **`test_client_idempotency_key_on_mutating_only`** — Asserts: an `Idempotency-Key` header rides every `MUTATING_ENDPOINTS` command and is absent on `GET /projects`. Why: §4 R9 idempotency.
4. **`test_token_never_logged_or_in_url`** — Asserts: across a command + SSE open, the token appears in no log sink and in no request URL/query (only the header). Why: forbidden pattern 3; §16.
5. **`test_sse_parses_each_event_tag`** — Asserts: each of the 8 `event` tags validates into its typed branch with domain-enum fields intact (`step-state.status`∈`StepState`, `validation.scope/severity`, `gate-needed.gate`∈`GateKind`). Why: §4 SSE taxonomy (D15-tightened).
6. **`test_sse_rejects_unknown_tag_and_malformed`** — Asserts: a frame with an unknown `event` tag, and one with a missing required field, are rejected at the boundary (no silent coercion). Why: §4 strict (`extra="forbid"`) boundary.
7. **`test_sse_error_event_code_tolerance`** — Asserts: an `error` event with an unrecognized `error.code` degrades to `SYSTEM`; a known code passes through. Why: carry-forward 0.2/D10b; `parseErrorCode`.
8. **`test_sse_reconnect_sends_last_event_id_and_drops_replayed`** — Asserts: after events id=1,2,3 then a drop, reconnect sends `Last-Event-ID: 3`; a replayed id≤3 is dropped, id=4 is delivered once. Why: §3 reconnect-replay.
9. **`test_sse_schema_type_parity_with_generated`** — Asserts (compile-time + a runtime tag-coverage check): every generated `SseEvent` member's `event` tag has a Zod branch, and `z.infer` is type-equal to the generated union (a future-added event fails this). Why: root CLAUDE.md "import the generated type, don't duplicate"; drift guard.
10. **`test_projection_is_pure_and_idempotent`** — Asserts: `projectEvent` is a pure reducer; applying the same event id twice == applying once; replaying the full stream reproduces the read-model. Why: §3 thin observer; forbidden pattern 2.
11. **`test_projection_holds_no_durable_authority`** — Asserts: the read-model is reconstructed solely from the stream (no external/cached authority); a fresh projection + replay == the live state. Why: forbidden pattern 2 (sidecar = source of truth).
12. **`test_token_handoff_exposes_to_renderer_only`** — Asserts: `createLoopbackTokenChannel` exposes the token via the bridge getter and not on `window`/global or any log; the bridged client carries it. Why: §4/§16 parent→child channel.
13. **`test_ui_responsiveness_slow_stage_does_not_block` (§21)** — Asserts: with a mock sidecar whose stage X is slow, `client.startRun()` resolves promptly (ack) **and** SSE heartbeat + unrelated `progress` events keep arriving while X is pending. Why: §21 falsifiable UI-responsiveness gate.

## Things to flag at Step 2.5
1. **SSE transport + token presentation (load-bearing — shapes the IPC client surface + the §16 boundary).**
   Native `EventSource` cannot set custom headers, so it can't carry `X-AISims-Token` except via a URL query
   param — which gets logged by servers/proxies/devtools and violates forbidden pattern 3 / §16. Options:
   **(A)** fetch + `ReadableStream` SSE reader, token in the header — full control, secure; we own minimal SSE
   frame parsing. **(B)** native `EventSource` + token in the URL — simplest, but leaks the token → reject.
   **(C)** `EventSource` + cookie-borne token — extra cookie/CSRF machinery on loopback, over-built.
   **My default vote: (A)** — it's the only option that keeps the token header-only (rule 3) and gives us
   `Last-Event-ID` control. *This is the one decision worth a user nod — escalation-flagged to the lead.*
2. **React + Vite now, or defer to 7.3?** The deterministic thin-observer core (client/SSE/projection) is
   framework-agnostic TS; the visible screens are 7.3. **Default: defer** — 7.1 ships the headless core + the
   Electron shell loading a static placeholder renderer; keeps the dep surface to `zod` + `electron`. React/Vite
   + testing-library arrive with the first screens (7.3).
3. **Zod boundary: hand-author (mirroring the generated union, parity-guarded) vs. codegen from the JSON
   Schema?** **Default: hand-author** in `sse-schema.ts` with the RED-#9 compile-time parity guard — no new
   codegen toolchain in the UI track, and the CI drift gate already guards the generated TS types; the Zod schema
   is purely the runtime validator. Revisit codegen if the surface grows past the SSE union.
4. **Reconnect dedupe: cursor-drop in the SSE reader, idempotent projection, or both?** **Default: both** —
   defense in depth: the reader drops `id ≤ lastEventId` after reconnect, and the projection is idempotent on
   repeat ids. A server that replays inclusively can't double-count either way.
5. **Mock-sidecar fixture shape for §21.** The fixture (`test/fixtures/mock-sse.ts`) models command POST →
   immediate ack body (the §4 response) with the slow work surfacing only as delayed SSE events for that stage,
   plus a periodic heartbeat. **Default:** assert ack-resolves-promptly + heartbeat-keeps-ticking against this
   fixture (no real sidecar; no wall-clock flakiness — drive time with a fake timer / injected clock).
