### R-001 — Image-to-3D cloud providers
**Findings:** **fal.ai** is the strongest aggregator — one uniform async API (`queue.submit→request_id`, `queue.status`, `queue.result`, webhooks) fronting Tripo3D v2.5, Hunyuan3D v2/v3, TRELLIS 2, Rodin, Meshy, TripoSR. **Tripo3D v2.5** has the best *game* topology (quad-dominant, `face_limit`, orientation control, PBR; +$0.05 quad; ~$0.15–0.30/gen). Hunyuan3D (WaveSpeed v3, $0.225–0.675) = best price/fidelity but dense triangles (needs decimate). TRELLIS 2 (fal $0.25–0.35; Replicate firtoz/trellis ~$0.039) = cheap detail, dense triangles. Rodin = premium quad, $0.50–1.50. TripoSR/SF3D = fast cheap draft tier only. **Every viable provider is async submit+poll/webhook — none synchronous.**
**Impact:** One `Image3DProvider` interface = `submit(image,params)→job_id` · `poll(job_id)→{status,progress,urls}` · `fetch(urls)→GLB+textures`. Persist `provider+job_id` in run state → reconcile-resume re-polls instead of re-billing. Normalize on GLB+PBR; Blender remesh/decimate pass for non-quad models. ⚠️ **Tripo result URLs expire in 24h** — download promptly; reconcile treats expired-but-succeeded as needs-redownload.
**Recommendation:** First real adapter = **fal + Tripo3D v2.5** default; bakeoff swaps model-id across Tripo/Hunyuan3D/TRELLIS with no transport change.
**Risk/Fallback:** Vendor-stated quality must be bakeoff-confirmed; Sims needs DST/DDS textures + specific shaders that no generic GLB satisfies (Blender+archetype stages mandatory). Fallback: flip fal model-id → Hunyuan3D/TRELLIS; second vendor = WaveSpeed Hunyuan3D V3; cost fallback Replicate; premium Rodin.
**Sources:** fal.ai model/API docs (Tripo v2.5, Hunyuan3D v2, TRELLIS 2, TripoSR), WaveSpeed Hunyuan3D V3, Meshy docs, Hyper3D Rodin API, Replicate firtoz/trellis, Tripo platform docs, 3DAIStudio 2026 comparison.

### R-002 — Local Apple-Silicon image-to-3D
**Findings:** A local Mac path is **realistic only as a degraded, geometry-only fallback** — not quality-equivalent. The only end-to-end Mac option is the **TRELLIS.2 MPS port** (shivampkumar/trellis-mac, Apr 2026): ~3.5 min on M4-class, ~15–18 GB peak (48 GB is ample — RAM is *not* the bottleneck), GLB/OBJ but **vertex-colors only, texture baking stubbed**. Hunyuan3D-2.1-mac, SF3D/SPAR3D (official "experimental" MPS), TripoSR all run but texture/PBR is the part that breaks on MPS (CUDA ops nvdiffrast/xatlas get stubbed). TripoSG = CUDA-only.
**Impact:** Local provider = **geometry-only**, feature-flagged, with a quality/latency warning; push texturing downstream (Blender/cloud texture pass). Vendor-pin a known-good fork commit + smoke test (fragile community forks).
**Recommendation:** **Cloud is the production path; local is an optional offline escape hatch.** If shipped, use the TRELLIS.2 MPS port, geometry-only.
**Risk/Fallback:** Young single-maintainer fork, weak texturing; fall back SF3D/SPAR3D, else drop local entirely and make cloud the only path.
**Sources:** lilting.ch TRELLIS.2-MPS writeup, HN thread, shivampkumar/trellis-mac, Brainkeys Hunyuan3D-2.1-mac, Stability SF3D/SPAR3D docs, VAST TripoSG, meshfinity.

### R-003 — Mac-runnable DBPF tooling **(the A2 answer)**
**Findings:** **@s4tk (Sims 4 Toolkit, TypeScript/Node)** is the **only** mature, actively-shipped, cross-platform Sims-4 DBPF **read+writer** — runs natively on Apple Silicon, **zero .NET/Wine/VM**. `Package.from(buffer)` / `getBuffer()`; `MappedModel` CRUD (add/delete/getByKey by TGI) maps directly onto clone-and-replace. Native models for tuning/SimData/STBL/ObjectDefinition/XML + **DST/DDS textures** (DdsImageResource, handles Sims "shuffled" DST). **BUT: no first-class GEOM model — mesh carried as opaque `RawResource` bytes.** Compression = ZLIB (modern packages; no RefPack write, not needed). It's pre-release 0.x (last update 2024) — must vendor-pin. Sims 4 Studio Mac (Aurora, Apple-Silicon GUI) has **no CLI/headless** mode. Python DBPF libs are weak/dormant (s4py) or Sims-2-only.
**Impact:** Export subsystem = **@s4tk Node worker** (the PACKAGER). Pipeline hands it `{donor.package, GEOM bytes, DST textures, tuning/SimData edits, target TGI keys}` → finished `.package`. Hard scope split: **MESH stage (→GEOM bytes) is separate from PACKAGE stage (s4tk embeds bytes).** Donor packages sourced from the **user's own game install** at runtime (licensing). Add DBPF round-trip + test-install gate to validation from day one.
**Recommendation:** Build export on the **@s4tk Node stack** (models+compression+hashing+images+xml-dom); vendor-lock versions.
**Risk/Fallback:** **HIGH on the mesh half** — no verified headless Mac GEOM authoring (see R-008). MEDIUM: s4tk pre-release/single-maintainer; community-reverse-engineered formats can break on EA patches. Fallback: custom ZLIB-only DBPF writer (DBPF spec is simple) reusing s4tk resource encoders; worst case ship loose resources + a one-click S4S project for manual finish.
**Sources:** @s4tk/models npm + GitHub source, @s4tk/compression source, sims4toolkit.com, Frankk S4TK build guide, S4S Aurora Mac beta, S4S "no CLI" thread, thequux/s4py, Kuree Sims4Tools wiki (type IDs).

### R-004 — Sims 4 object structure & game-ready geometry
**Findings:** A placeable Build/Buy package = DBPF of typed resources: **OBJD** (0xC0DB5AE7, catalog/behavior root, references tuning by 64-bit instance) + **COBJ** (catalog: price/sort/swatches) + **MODL/MLOD** (model + per-LOD) + **GEOM** (0x015A1849, mesh) + **FTPT** (footprint) + **RIG** (skeleton/slots, even decor needs a stub) + **SLOT** + **DST/_IMG** textures + **thumbnails**. Missing core resources → opens only in Warehouse, won't place. **Functional behavior lives in the donor's TUNING (components + SuperAffordances), NOT the mesh** → clone a *working EA functional donor*, replace only mesh/textures/swatches, keep OBJD→tuning→FTPT→RIG→SLOT. Lamp=light component; stereo=audio affordances; mirror=reflective+practice affordances. **Geometry:** 3–4 LODs + shadow LODs; ~**2000 tris/tile** LOD0 (per occupied floor tile), LOD1≈30%, engine tolerates ~20k/item. **AI-mesh pitfalls: scale (rescale to donor bbox), origin (floor-centered), NORMALS (S4S drops them → invisible meshes; must recalc/transfer), UVs (valid uv_0 + uv_1), meshgroup-count must match cloned package.**
**Impact:** (a) Blender stage owns the **game-ready gate**: rescale, origin, normal recalc/transfer, UV validation, meshgroup match, LOD-chain + shadow-LOD gen under per-tile poly budget. (b) Archetype-map + export = **donor-clone-and-graft** with a versioned `Archetype→Donor` registry. (c) Validation asserts required resource set + OBJD tuning instance resolves. Functional overlay = *which donor archetype*, not extra mesh.
**Recommendation:** **Clone-a-donor for everything**; never hand-author resources. Reuse S4S/s4tk serialization, never re-derive binary parsers.
**Risk/Fallback:** EA patches shift tuning → version-pin + re-validate donor library. AI mesh may need retopo beyond auto-decimate. Fallback: failing the gate → surface mesh for manual S4S import, OR ship as decorative-only (deco donor), OR substitute donor's original mesh; degrade behavior to nearest simpler archetype rather than emit broken functional.
**Sources:** S4S "Components of an EA Object", Sims4Group/Modders-Reference/Kuree type-ID tables, S4S "deco object functional" thread, Sims 4 Tuning 101 (Medium), Simandy poly/LOD guide, S4S normals thread.

### R-005 — Graph orchestration
**Findings:** **LangGraph 1.x** (1.0 GA Oct 2025; 1.2.5 June 2026) — pure-Python, in-process, no server. **Native local SQLite checkpointer** (durable state, zero infra). First-class HITL: `interrupt()` persists state + `Command(resume=...)` (survives process exit = the approval-gate pattern). Configurable durability (`exit`/`async`/`sync`). Mock-or-real = swap InMemory↔Sqlite + config-gate node logic. ⚠️ **Cloud-job reconcile is NOT free**: nodes re-run from top on resume → wrap external calls in `@task` (checkpointed), store `job_id`, poll-on-resume; **app must own the startup reconciler + single-writer lock** (LangGraph has no watchdog/auto-resume/dup-prevention — Diagrid critique). Time-travel via `get_state_history`/`update_state`.
**Impact:** `StateGraph`, one node/subgraph per stage, typed State carrying artifacts + provider job_ids + status; one SQLite file under app data dir, one `thread_id` per project/run. Cloud steps = two-phase (submit `@task` + poll/reconcile node). Approval gates = `interrupt()`. `durability='sync'` for cloud/long stages, `exit`/`async` for cheap ones. Host owns startup reconciler + single-writer lock.
**Recommendation:** **LangGraph 1.x + langgraph-checkpoint-sqlite**, pinned together.
**Risk/Fallback:** No auto failure-detection/dup-prevention (app handles); resume re-runs node → idempotency required to avoid double-billing; LangChain-ecosystem churn/coupling; SQLite single-writer. Fallback: **Apache Burr** (state machine + SQLite persister + local trace UI, ASF-governed) — stage funcs + reconcile pattern port over; Temporal only if true durable execution later justifies a server.
**Sources:** LangGraph 1.0 changelog, PyPI, durable-execution/interrupts/functional-API/time-travel docs, SqliteSaver ref, Diagrid critique, Apache Burr 0.42 announce + site, Temporal/LlamaIndex/Prefect comparisons.

### R-006 — Desktop shell + Python sidecar (resolves OQ1)
**Findings:** Best fit = **Electron shell + Python sidecar over localhost HTTP + SSE** (+ small WS/HTTP control channel for cancel). Electron = mature default for complex web-first UIs, deepest macOS packaging/auto-update, no Rust. Python sidecar (FastAPI on dynamic free port) keeps all heavy logic in one language; SSE streams graph transitions/progress/logs (trivially resumable — sidecar owns durable state, UI re-subscribes). **Blender = separate CLI subprocess** (GPL boundary clean: subprocess IPC ≠ derivative work; per-job isolation; restartable) — **never the bpy pip module in-process**. ⚠️ **macOS notarization of the PyInstaller sidecar = highest-risk packaging task** (nested .so/.framework + base_library.zip break notarization unless every nested binary is deep-signed w/ Hardened Runtime). **Sidecar lifecycle is core infra** (free-port pick, /health poll, supervised restart, process-tree kill — PyInstaller spawns parent+child; orphan-port bugs). Alts: Tauri (lighter <10MB/<0.5s but Rust + less-mature sidecar lifecycle), PySide6 (single-language, no IPC/port/sidecar — but non-web Qt UI).
**Impact:** Two-process topology; **sidecar = durable resumable job owner, UI = thin observer that can reconnect**. IPC contract: REST commands + SSE progress/logs + DELETE/WS cancel. Blender = external tool dep w/ subprocess wrapper + version detection + GPL boundary. **The @s4tk export worker (R-003) = a Node subprocess** the Python sidecar shells out to (Electron already bundles Node). macOS build pipeline (PyInstaller deep-sign + notarize + staple, + sign Electron) = CI'd early. Supervisor module = core infra.
**Recommendation:** **Electron + Python(FastAPI) sidecar, HTTP+SSE+cancel; Blender + @s4tk as subprocess workers.**
**Risk/Fallback:** Notarization fragility (verify end-to-end early); orphan sidecar/Blender processes; SSE reconnect (Last-Event-ID). Fallback: collapse to **PySide6** (one process, one signing target) if notarization/lifecycle too fragile; or **Tauri** if Electron footprint unacceptable (identical sidecar contract = low migration); python-build-standalone/Nuitka if PyInstaller signing fails.
**Sources:** Tauri+FastAPI+PyInstaller production writeup, Tauri sidecar docs + lifecycle/kill bug threads, Blender-as-module docs, Blender GPL license + ifrOSS derivative-work analysis, txoof/codesign + PyInstaller #5112 notarization, 2026 framework comparison, PySide6 QWebEngine.

### R-007 — Observability (genuine tradeoff to confirm)
**Findings:** **Langfuse v4** (self-host Docker Compose, **6 containers**: web/worker/Postgres/ClickHouse/Redis/MinIO) — **native OTel** (v4 SDK is an OTel SpanExporter; OTLP endpoint), **first-class multimodal artifact lineage** (images/meshes/DBPF → MinIO, rendered inline on trace timeline), cost/latency, sessions, human annotation. Fits 48 GB but heavy. **Arize Phoenix** — **single container** (or `pip install arize-phoenix` + `phoenix serve`), OTel/OpenInference-native, auto-instruments LangGraph, Human Annotations — **lightest local install**, but weaker durable-artifact/blob lineage (inline image display, no presigned blob pipeline). **LangSmith self-host = Enterprise-license-gated → rejected.** Pure custom OTel = build everything + experimental GenAI-semconv "broken span lineage across async" risk.
**Impact:** Instrument with **OTel** across all stages (LLM nodes + non-LLM Blender/validation/export spans); backend = swappable OTLP sink. Artifacts attached to producing span → lineage prompt→plan→image→mesh→cleanup→export→test-install. Each generation run = a session; user accept/reject = scores/annotations.
**Recommendation:** **Langfuse v4** for richest lineage (this pipeline is artifact-heavy) — **but** the 6-container Docker dependency is heavy for "a few known users" on a desktop. **Phoenix** is far more shippable. → **decision point for the user** (see DECISIONS ADR-007). Because both are OTel, switching is low-cost.
**Risk/Fallback:** Langfuse v4 GA-stability (v3 is proven); MinIO endpoint config footgun; 6-container ops/startup weight. Fallback: **Phoenix** (single container, portable OTel code, filesystem artifacts).
**Sources:** Langfuse self-host/blob/OTel/LangGraph docs + PyImageSearch v4 writeup, Phoenix docker/multimodal/vs-Langfuse docs, LangSmith self-host pricing, OTel GenAI semconv blog.

### R-008 — Blender automation on macOS (the GEOM bottleneck)
**Findings:** `bpy` is on PyPI with a **native Apple-Silicon wheel** (`bpy==5.1.2`, requires **Python ==3.13**); Blender 5.x is **Apple-Silicon-first** (5.0 dropped Intel Mac). bpy module behaves as `--factory-startup` (deterministic for free) but has headless limits (GPU import restricted in background, **no signal handlers/Ctrl-C/crash logs**, GPU sharing conflicts when embedded). CLI (`blender --background --factory-startup --python`) = hard process isolation + full GPU render. **MCP excluded from production: both Blender MCP servers need a live GUI + run nondeterministic arbitrary Python.** ⚠️ **THE bottleneck: no maintained, headless, Blender-5 Sims-4 GEOM exporter exists.** Existing exporters are GUI/old-Blender-bound (S4S 2.70–2.79; SmugTomato Sims-3 2.8x; a Jan-2026 "SimGeom" with no canonical repo). GEOM is a documented binary format (s4py/s4sdk read/write) so a custom writer is feasible-but-scoped. Both CLI & bpy can install/enable a pinned add-on per run.
**Impact:** **Toolchain pin: Blender 5.1.x + Python 3.13 + bpy 5.1.2, Apple-Silicon-only.** `BlenderBackend` interface w/ two impls (bpy-in-process + CLI-subprocess) for the spike A/B. **GEOM export = its own vendored, version-pinned sub-dependency + DBPF/GEOM validation step** — the riskiest node, isolated so a Blender upgrade can't silently break it. Stage stays local/offline.
**Recommendation:** **Hybrid: deterministic core + CLI-subprocess as the production execution path** (GPL isolation, crash containment, decouples sidecar Python version from Blender's 3.13, full render), bpy-module for spike/fast iteration. **MCP = optional dev-only copilot, never a stage executor.** *(Synthesis note: R-008 leaned bpy-core, R-006 leaned CLI-subprocess; reconciled toward CLI-subprocess-primary — Brain 2 to confirm.)*
**Risk/Fallback:** **GEOM export may have NO working Blender-5 headless path** → the first spike must settle it. Fallbacks: pinned-old-Blender GEOM microservice; **custom GEOM writer (s4py/s4sdk)**; worst case a Windows helper VM for the mesh stage only. Validate GEOM correctness against a real in-game install, not just file-parse.
**Sources:** bpy PyPI, Blender-as-module + command-line docs, Blender 5.1 notes + Intel-drop forum, official Blender MCP + ahujasid/blender-mcp, SmugTomato GEOM repo, thequux/s4py.

### R-009 — Concept image generation
**Findings:** 2026 leader = **FLUX.2 [pro]** (32B; Artificial-Analysis photoreal lead) with a **native `transparent_bg` RGBA toggle** → clean alpha silhouette → **skip rembg**, exactly what image-to-3D wants. Available on **WaveSpeed** (no cold starts), Replicate, fal, OpenRouter-style. Image-to-3D inputs want: isolated single subject, even diffuse light, 3/4 elevated view, 512–2048px; alpha used directly as mask. ~$0.015–0.03/img. **FLUX.2 [dev]** (~$0.008–0.013) cheaper bulk tier (may need rembg). **Z-Image Turbo** (~$0.005, ~1s) proven image-to-3D input (powers open TRELLIS.2 text-to-3D). Local fallback: **FLUX.2 [klein] via MLX** on 48 GB (~30–40s/1024). Avoid GPT Image 2 (no alpha, pricey).
**Impact:** `ImageGenProvider` interface, **WaveSpeed default** + Replicate/fal/OpenRouter alternates (same FLUX.2 id). Fixed prompt template ("single isolated object, centered, plain seamless studio bg, even diffuse light, slight 3/4 front, product photography") + `transparent_bg=true` + pinned seed (resumability) + 1024–1536px. Emit N candidates + silhouette-quality score gate before 3D. Keep rembg fallback path.
**Recommendation:** **FLUX.2 [pro] via WaveSpeed (transparent_bg)**, candidate-and-score loop.
**Risk/Fallback:** Prices/`transparent_bg` availability vary by endpoint (re-verify); silhouette quality is prompt/seed-dependent (score loop is load-bearing). Fallback: FLUX.2 pro on Replicate/fal; FLUX.2 dev/Z-Image + explicit rembg; local klein+rembg offline; multi-view (+$0.15) if single view reconstructs poorly.
**Sources:** FLUX.2 pro guide (transparent_bg), Flux Wikipedia timeline, BFL pricing, fal Hunyuan3D v3 input guide, 3DAIStudio model comparison, WaveSpeed FLUX/Z-Image pages, MLX FLUX.2 ports.

### R-010 — Eval harness framework
**Findings:** **DeepEval v4** (4.0.3, May 2026) = Python-native "pytest for LLMs" (`deepeval test run`, goldens, CI gating, 50+ metrics). **DAGMetric** = deterministic structured-output gating (schema/section checks) with **GEval** (LLM-judge) embeddable at leaves. **First-class multimodal** (`MLLMTestCase`/`MLLMImage`, ImageCoherence/Helpfulness/VIEScore/MultimodalGEval) + **ArenaTestCase** (native pairwise → the image-to-3D **bakeoff** + human-preference). Non-LLM numeric checks become **custom `BaseMetric`** wrapping **trimesh** (watertight/winding/broken-faces), PyMeshLab, Chamfer/Hausdorff (mesh-QA) and **torchmetrics CLIPScore**/SSIM/LPIPS (image). Promptfoo = config-first, JS-centric, **no image/mesh assertions**, and **acquired by OpenAI (Mar 2026)** → roadmap pivot (vendor-neutral risk). Pure pytest = max control, unavoidable for deterministic stages.
**Impact:** **DeepEval as the single backbone** for all 9 harnesses (dev/CI only, not shipped): prompt-to-plan→DAG+GEval; concept-image→MultimodalGEval+CLIPScore; bakeoff→ArenaTestCase+mesh metrics; Blender/mesh-QA→BaseMetric(trimesh/Chamfer); archetype/overlay/export→DAG+syrupy/pydantic goldens; human-preference→ArenaTestCase. `tests/evals/` per stage + `evals/metrics/` BaseMetric package; goldens in Git-LFS/DVC. Vendor-neutral judge model. PR CI = curated set, nightly = full.
**Recommendation:** ~~DeepEval v4 primary~~ → **REVISED by the eval-deepdive** (post-LangSmith-lock; see ADR-008
+ `tasks/we77jl8cj.output`): **LangSmith-native evals = backbone** + a **framework-agnostic metric component
layer** (trimesh/Open3D/torchmetrics/IQA-PyTorch + **Blender-headless render bridge**) + **pytest/pydantic/
syrupy** substrate; **DeepEval demoted to optional** (collides with LangSmith if its tracing is enabled).
Decisive finding: **no framework has native 3D-mesh metrics — mesh eval is custom Python everywhere**, so the
framework choice is about datasets/CI/pairwise/human-pref, not metrics.
**Risk/Fallback:** LLM-judge nondeterminism/drift; heavy native deps (PyMeshLab/torch) on Apple Silicon; v4 recency; Confident-AI hosted-dashboard pull (stay OSS-local). Fallback: pure **pytest + pydantic + syrupy + trimesh + torchmetrics + hand-rolled LLM-judge** (DeepEval already runs on pytest → low loss). Promptfoo only as a targeted red-teaming secondary.
**Sources:** DeepEval docs (intro/DAG/GEval/multimodal/custom-metrics/CI/datasets) + v4 blog + Context7, Promptfoo assertions/custom-provider docs + OpenAI acquisition, torchmetrics CLIPScore, trimesh.repair, IQA-PyTorch.

## Cross-cutting synthesis
1. **Every cloud stage is async submit+poll/webhook** (R-001/009) → the resumable graph (R-005) persists provider job_ids and reconciles on restart. The architecture's spine is *job-id durability*.
2. **Mac feasibility is real but split** (R-003/008): **packaging** is solved on Mac (@s4tk Node); **mesh→GEOM** is the unsolved, #1-risk node → first spike.
3. **Three runtimes + Blender** (R-006): Electron/Node (shell) · Python (pipeline sidecar) · Node (@s4tk export worker) · Blender CLI (mesh worker). Sidecar = durable job owner; UI = thin observer.
4. **Toolchain pins** (R-008): Blender 5.1.x + Python 3.13 (bpy) + Apple-Silicon-only for the Blender/local-3D paths; cloud paths stay cross-platform.
5. **OTel is the instrumentation contract** (R-007) → backend (Langfuse/Phoenix) is swappable.
