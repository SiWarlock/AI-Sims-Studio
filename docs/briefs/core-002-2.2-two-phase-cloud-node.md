# /tdd brief — two_phase_cloud_node

## Feature
The **two-phase cloud-node pattern** for the pipeline graph: a `@task`-wrapped **idempotent submit** whose result (the `ProviderJobRef`) is **checkpointed before any side effect**, then a **poll/reconcile node** driving the async provider lifecycle (submitted→running→succeeded/failed/expired) to terminal and fetching outputs on success — provably **no double-submit on replay** (R9), on mock providers.

- **Related context:** 2.1 (the StateGraph + `PipelineState.providerJobRefs` + checkpointer — landed `b1cabd2`). The **frozen provider contracts (0.5a — `aisims_contracts/providers.py`)**: `ProviderJobRef{provider,model,jobId,submittedAt,expiresAt?}`, `PollResult{status,progress?,urls?,usage?,error?}`, `PollStatus{submitted,running,succeeded,failed,expired}`. The **0.8 mock async providers** (`adapters/mock/providers.py`: `MockImage3DProvider`/`MockImageGenProvider`, `submit→ProviderJobRef`, `poll→PollResult` cycling `succeed_after_polls=3`, scratch-guarded `fetch`). langgraph 1.2.5 functional API: `@task` results are **checkpointed inside a StateGraph node** (skip completed work on resume), but an **unfinished** task re-runs on resume — so submit must be idempotent (Lesson 11 durability-at-runtime note).

## Acceptance criteria (what "done" means)
- [ ] A `@task`-wrapped submit (inside the cloud node) whose RESULT (the `ProviderJobRef`) is **checkpointed** — on resume a **completed** submit is NOT re-executed (langgraph @task result-cache).
- [ ] The cloud node writes the returned `ProviderJobRef` into `PipelineState.providerJobRefs` (keyed by item/step id) **before** the poll phase — the reconcile-spine handle survives a checkpoint.
- [ ] A poll/reconcile node reads the persisted ref and polls to a terminal `PollStatus`; on `succeeded` it `fetch()`es outputs (scratch paths into State); on `failed`/`expired` it surfaces `PollResult.error` (the §17 envelope) **without re-rolling it** (the reconcile *decisions* — expired→re-submit, GC'd→regenerate — are 2.4).
- [ ] **[R9 · no-double-submit pin]** a run interrupted after submit (ref persisted), then resumed, calls the provider's `submit` **exactly once** (a submit-counter proves it) and reuses the same `ProviderJobRef`.
- [ ] The cloud node takes its provider via **injection** (Protocol-typed `Image3DProvider`/`ImageGenProvider` from `aisims_contracts`) — **no hard-coded provider** (rule 2); registry-based provider *selection* is 2.3.
- [ ] `durability="sync"` is applied **at invoke** for the cloud-bearing run (the checkpoint — incl. the @task result — is written synchronously before proceeding); `build_graph` stays checkpointer-only (Lesson 11). The 'sync' convention is documented for the 2.3 caller.
- [ ] **No `packages/contracts` change** (cross-doc invariant: none, per the plan); no Step-contract field added — `ProviderJobRef` persists in checkpointed State, and the app-repo (queryable) persistence for the startup reconciler is a 2.4 store concern (a store column, not a contract change).
- [ ] All unit tests in `tests/graph/test_cloud_node.py` pass; `/preflight` clean.

## RED test outline (Step 2)
Tests in `tests/graph/test_cloud_node.py` (+ one in `test_resume.py` if the restart pin reuses its harness):

1. **`test_submit_persists_job_ref_before_poll`** — Asserts: invoking the cloud node calls `provider.submit` once, and `PipelineState.providerJobRefs[itemId]` holds the returned `ProviderJobRef` after the submit phase (before any poll). Why: §5 "persist `ProviderJobRef` before any side effect."
2. **`test_poll_drives_to_succeeded_and_fetches`** — Asserts: the poll node cycles the mock (submitted→running→succeeded at `succeed_after_polls`) then `fetch()`es; output scratch paths land in State. Why: §5 poll/reconcile node + the `PollStatus` provider lifecycle (0.5a).
3. **`test_failed_poll_surfaces_envelope_unrerolled`** — Asserts: an injected POLL failure yields `PollResult.status∈{failed,expired}` with the **same** `ErrorEnvelope` surfaced into State (identity/equality, not a re-rolled one). Why: §17 single failure contract, never re-rolled.
4. **`test_no_double_submit_on_resume`** — **[R9 PIN]** Asserts: interrupt the run after submit (ref persisted under a SQLite-file checkpointer + thread_id), drop+rebuild graph+saver, resume → `provider.submit` call-count stays **1** and the resumed run reuses the same `ProviderJobRef`. Why: §5 R9 "prevents double-billing under replay."
5. **`test_cloud_node_uses_injected_provider`** — Asserts: the cloud node calls the **injected** provider instance (no module-level/hard-coded provider; a spy provider records the calls). Why: rule 2 (adapter seam, no provider lock-in).
6. **`test_durability_sync_checkpoints_ref_synchronously`** — Asserts: invoking with `durability="sync"`, the `ProviderJobRef` is present in the persisted checkpoint immediately after the submit phase (read back from the saver). Why: §5 `durability='sync'` for cloud/long stages (Lesson 11: runtime arg).

## Things to flag at Step 2.5
1. **`@task` inside the StateGraph node vs the `@entrypoint` functional API.** 2.1 is a `StateGraph` (graph API). langgraph supports `@task` *inside* a graph node (results checkpointed). **My default vote: `@task` inside the existing StateGraph node** — reuse the 2.1 graph; don't switch to `@entrypoint`. (Verify the @task-in-node result-cache survives the SQLite saver across a rebuilt graph, same as 2.1's resume test.)
2. **Where `ProviderJobRef` persists.** State (checkpointed) only, or also the app-repo Step row now? **My default vote: checkpointed State (`providerJobRefs`) only** — the plan declares cross-doc-invariant *none*; the queryable app-repo persistence the **startup reconciler (2.4)** needs is a 2.4 store concern (a `StepRow` column / a job-ref table — a store change, not a frozen-contract change). Don't add a Step contract field here.
3. **R9 idempotency boundary.** `@task` caches a *completed* submit; an *unfinished* submit re-runs on resume (langgraph idempotency note). **My default vote: 2.2 pins the completed-submit-no-resubmit property on mocks** (test 4); the mid-flight true-idempotency-key (so a crash *during* the external call can't double-create) is a **Phase-3 real-adapter** Future TODO (mocks have no external side effect to double-create). Document the boundary.
4. **Provider injection seam on `build_graph`.** How does the (mock) provider reach the cloud node? **My default vote: an injection param on `build_graph`** (e.g. `providers: ProviderBundle | None`, mock default in tests) — the registry-based *selection* is 2.3. Keeps rule 2 clean (no hard-coded provider) and 2.1's no-arg tests green via the default.
5. **Which stages become cloud nodes in 2.2.** **My default vote: concept + mesh** (the two cloud-provider stages — image-gen + image-to-3D); plan/overlay/export stay 2.1 no-ops until their slices. Flag if wiring both now bloats the slice — wiring just `concept` and leaving `mesh` no-op is acceptable latitude.
