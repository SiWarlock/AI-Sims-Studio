# /tdd brief — bounded_parallel_scheduler

## Feature
The job/run engine's **bounded-parallel scheduler** (distinct from the graph): schedules item work with **two separate concurrency caps** — a *cloud-submit* cap and a *local-Blender-subprocess* cap (independent hot paths, human-set config knobs) — under **one active project**, **block-and-queue on saturation**, with **per-item failure isolation**. On mocks.

## Acceptance criteria (what "done" means)
- [ ] A `Scheduler` runs a batch of item-work **bounded-parallel** by a per-`ResourceKind` cap: `CLOUD_SUBMIT` work is capped at `cloud_submit_cap`, `LOCAL_BLENDER` work at `local_blender_cap` — **peak concurrency never exceeds the cap** (a concurrency-probe proves it).
- [ ] The **two caps are independent**: saturating the cloud cap does NOT consume Blender slots and vice-versa (a mixed batch proves both run to their own ceilings concurrently).
- [ ] **Block-and-queue on saturation**: the (cap+1)th unit **waits** for a slot to free (does not error, does not exceed the cap); all units eventually complete.
- [ ] **Per-item failure isolation**: one unit raising does NOT abort the batch — the other units complete, and the failure is captured **per-item** (a result/error map), never propagated to kill siblings.
- [ ] **One active project**: starting a second project's run while one is active is **rejected-or-queued** (not run concurrently) — a single-active-project guard.
- [ ] The two caps + the active-project policy are **config knobs** (a typed `SchedulerConfig` with `cloud_submit_cap` / `local_blender_cap`, validated ≥1); defaults are human-set.
- [ ] No `packages/contracts` change (cross-doc invariant: none). All unit tests in `tests/engine/test_scheduler.py` pass; `/preflight` clean.

## RED test outline (Step 2)
Tests in `tests/engine/test_scheduler.py`:

1. **`test_cloud_cap_bounds_peak_concurrency`** — Asserts: scheduling M>cap `CLOUD_SUBMIT` units, a concurrency probe (enter++/exit-- around a barrier) records **peak ≤ cloud_submit_cap**; all M complete. Why: §6 bounded-parallel cloud cap.
2. **`test_blender_cap_bounds_peak_concurrency`** — Asserts: same for `LOCAL_BLENDER` at `local_blender_cap`. Why: §6 separate local-Blender cap.
3. **`test_two_caps_are_independent`** — Asserts: a mixed batch (cloud + blender units) lets each kind reach its own cap concurrently; cloud saturation doesn't throttle Blender. Why: §6 "two separate caps — different hot paths."
4. **`test_block_and_queue_on_saturation`** — Asserts: the (cap+1)th unit waits (a release-gated probe shows it starts only after a slot frees), never exceeds the cap, never errors; all units finish. Why: §6 block-and-queue on saturation.
5. **`test_per_item_failure_isolation`** — Asserts: in a batch where one unit raises, the others all complete and the result map records the one failure (envelope/exception) per-item without aborting the batch. Why: §6 per-item failure isolation.
6. **`test_one_active_project_guard`** — Asserts: starting a second project while one is active is rejected-or-queued (the guard's chosen policy), never run concurrently. Why: §6 one active project.
7. **`test_scheduler_config_validates_caps`** — Asserts: `SchedulerConfig` rejects a cap < 1 (ValidationError); defaults are present. Why: config-knob validation (caps are human-set, ≥1).

## Things to flag at Step 2.5
1. **Concurrency model — asyncio vs threads.** The store is async and cloud/Blender work is I/O-bound (network / subprocess). **My default vote: asyncio** — two `asyncio.Semaphore`s for the caps (acquire naturally block-and-queues); sync mock provider calls get wrapped (`to_thread`) by the *caller's* work_fn, so the scheduler bounds **async callables**. Tests use `async def` mock work.
2. **One-active-project policy — reject vs queue.** **My default vote: reject a second concurrent project** (raise a clear `ProjectBusyError`) for 2.3 — the engine runs one project at a time (§6); a queue of pending projects is a later UX concern. Flag if you'd rather queue. (Note: this is a scheduler-level guard, **distinct** from the 0.9 single-writer lock, which is process-level — don't conflate; the lock can be referenced but the active-project guard is its own thing.)
3. **Scope boundary — primitive only vs graph-driving now.** **My default vote: 2.3 = the standalone bounded-parallel primitive** (mock async work_fn); the registry-selection + `build_graph`-per-item driving (Lesson 13) lands in the **run-start integration (2.4-adjacent)**, NOT here. Keeps 2.3 reviewable + matches §6 "distinct from the graph." Flag if you want a thin graph-driving seam in-slice.
4. **`SchedulerConfig` home.** No config module exists yet. **My default vote: define `SchedulerConfig` in `scheduler.py`** (a small pydantic model, the two caps + validation) — a project-wide config module is a later concern; don't build it now. The full cross-cutting config (price table, registries, paths, timeouts) is out of scope.
5. **Failure-isolation result shape.** **My default vote: return an ordered result map** `list[Result | FailedUnit]` (or `dict[item_key, …]`) pairing each input unit with its outcome (value or captured error), so the caller sees exactly which items failed — mirrors the §6 per-item isolation intent. The §17 error-taxonomy *classification* of those failures is 2.5.
