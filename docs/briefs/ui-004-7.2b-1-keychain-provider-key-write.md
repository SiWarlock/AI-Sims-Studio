# /tdd brief — keychain_provider_key_write

> **SAFETY (root CLAUDE.md rule 5): secrets live ONLY in the OS keychain — never in DB, logs, or traces.** This
> slice is the UI-side keychain WRITE path; the secret-handling core gets its OWN commit; redaction is test-pinned.

## Feature
The OS-keychain **write** path for provider API keys (revised D3 = shared NAMED entry, interop proven by spike
7.2b-0). A main-process `KeychainWriter` over **`@napi-rs/keyring`** stores each provider key in a login-keychain
generic-password entry at **`service="AISimsCreator"`, `account=<providerId>`**; it's exposed to the renderer over
a **narrow, sender-gated, WRITE-ONLY** IPC bridge — `setProviderKey` / `hasProviderKey` / `deleteProviderKey`,
and deliberately **no `getProviderKey`** (the secret is never read back into the renderer; the Python sidecar reads
it, 7.2b-2). Mock-first: the `@napi-rs/keyring` boundary is injected, so unit tests touch no real keychain.

## Acceptance criteria (what "done" means)
- [ ] **Write to the locked-in naming.** `KeychainWriter.setProviderKey(providerId, key)` writes via the injected
      keyring boundary to `service="AISimsCreator"`, `account=providerId`; the value reaches `Entry.setPassword`.
- [ ] **`hasProviderKey` / `deleteProviderKey`.** `has` returns true after a set, false for an unset provider and
      after a delete; `delete` removes the entry (idempotent — deleting an absent key is a no-op, not an error).
- [ ] **WRITE-ONLY bridge surface.** The exposed renderer surface is **exactly** `{setProviderKey, hasProviderKey,
      deleteProviderKey}` — **no `getProviderKey`** (the secret is never returned to the renderer). Single
      allowlisted IPC channel (`default→reject`), **top-frame sender-gated** (Lesson 6), composed into the existing
      `window.aisims` (Lesson 6 helper; token + fs preserved).
- [ ] **Rule-5 redaction (own commit).** The key value NEVER appears in any log/console sink, in the writer's
      `repr`/`toString`, or in an error message (a redaction test feeds a known secret + asserts it's absent from
      every surface). A keychain failure surfaces a typed, **redacted** error.
- [ ] **Locked-keychain path.** A locked/unavailable keychain surfaces a typed `KeychainUnavailableError` (not a
      crash) the onboarding screen can render a remediation for.
- [ ] All unit tests in `apps/desktop/test/` pass; `/preflight` clean. No real keychain touched in tests (injected boundary).

## RED test outline (Step 2)
1. **`test_set_provider_key_uses_locked_naming`** — Asserts: `setProviderKey("tripo", k)` → injected `Entry("AISimsCreator","tripo").setPassword(k)`. Why: §18; the shared secret-name contract.
2. **`test_has_and_delete_semantics`** — Asserts: `has` true after set / false unset / false after delete; `delete` of an absent key is a no-op. Why: §18.
3. **`test_bridge_surface_is_write_only_three_methods`** — Asserts: exposed keys == `{setProviderKey, hasProviderKey, deleteProviderKey}`; **no `getProviderKey`**; a non-allowlisted channel method rejects (`default→null`). Why: rule 5 (secret never read back to renderer) + Lesson 6.
4. **`test_sender_frame_gated`** — Asserts: the keychain IPC handler rejects a non-top-frame sender. Why: Lesson 6 (renderer↔main boundary).
5. **`test_key_value_never_leaks`** — Asserts: a known secret fed through write/error/`repr` appears in **no** log/console sink, no `toString`, no error message. Why: **rule 5 redaction** (this is the own-commit safety pin).
6. **`test_locked_keychain_surfaces_typed_error`** — Asserts: the injected boundary raising a lock/availability error → a typed `KeychainUnavailableError` (redacted), not a throw of the raw error. Why: spike caveat; onboarding remediation.
7. **`test_provider_id_sanitized`** — Asserts: an empty / whitespace / control-char providerId is rejected before reaching the keychain. Why: rule 5 (no malformed account injection).
8. **`token + fs bridges still exposed`** (regression) — Asserts: composing `keychain` into `window.aisims` preserves `getToken` + `fs`. Why: Lesson 6; no 7.1/7.2c regression.

## Things to flag at Step 2.5
1. **`providerId` validation — known set vs any sanitized non-empty string.** **Default: any sanitized non-empty
   string** (the provider registry is open, ADR-010; the keychain account is just the provider id) — but reject
   empty/whitespace/control chars (RED #7).
2. **Bridge is write-only (no `getProviderKey`).** **Default: yes** — the renderer writes + checks presence +
   deletes; it never reads the secret back (the sidecar reads it, 7.2b-2). This is the rule-5 crux.
3. **`@napi-rs/keyring` injection boundary.** **Default: inject a `KeychainEntry` factory interface**
   (`setPassword`/`getPassword`/`deletePassword`) so unit tests use a fake; the real `@napi-rs/keyring` `Entry` is
   the prod impl (typecheck-only, like the 7.1/7.2c native boundaries).
4. **Locked-keychain typed error.** **Default: `KeychainUnavailableError`** (redacted) → onboarding shows an
   "unlock your keychain" remediation. Folds the spike's minor caveat.
