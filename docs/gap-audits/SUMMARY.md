### [anchors-dag] · **load-bearing**
**Finding:** Hidden cross-edge collapses the two 'independent' spike-gated tracks C (Sims export) and D (Mesh/Blender GEOM) into one. §4a lists Track C (@s4tk export) and Track D (Blender game-ready GEOM) as separate 'independent parallel build tracks,' but the worker contract in §4a item 4 makes ExportJob CONSUME 'GEOM bytes' produced by BlenderJob, and ADR-005 states the 'hard split: MESH stage (→GEOM bytes, ADR-006) is separate from PACKAGE stage (s4tk embeds bytes).' **Evidence:** ARCHITECTURE_DRAFT §4a 'Independent parallel build tracks' lists Track C and Track D separately + worker-contract item 4 (ExportJob in: donor+GEOM+textures); ADR-005 'Hard split: MESH stage (→GEOM bytes) is separate from PACKAGE stage'; CLAUDE_CODE_HANDOFF S1 couples '@s4tk clone-a-donor + a headless GEOM path … via test-install'; DIAGRAM_PLAN diagram 4 (clone-a-donor) shows Blender GEOM feeding @s4tk in one flow.

**Proposed fix:** In §4a, stop labeling C and D as fully independent. State which.

### [decisions-consistency] · **load-bearing**
**Finding:** ADR-002 locks `langgraph-checkpoint-postgres`, but the ONLY research that informs it (R-005) exclusively researched and recommended `langgraph-checkpoint-sqlite`. The Postgres-for-checkpoints choice rests entirely on ADR-009 (a separate app-data-store decision the checkpointer research never contemplated), not on any evaluation of PostgresSaver maturity/lifecycle/concurrency under a desktop-bundled Postgres. Compounding evidence the design was reasoned about SQLite and not re-derived for Postgres: ADR-002 still mandates a 'single-writer lock' (a SQLite single-writer limitation) even though Postgres natively supports concurrent writers.

**Evidence:** RESEARCH.md R-005 line 54 'Recommendation: LangGraph 1.x + langgraph-checkpoint-sqlite, pinned together' and line 52 'Native local SQLite checkpointer' (PostgresSaver never mentioned); DECISIONS.md ADR-002 line 41 'LangGraph 1.x + langgraph-checkpoint-postgres ... aligns with ADR-009's Postgres store'; ADR-002 'single-writer lock' carried from R-005's 'SQLite single-writer' note (R-005 line 55).

**Proposed fix:** Either (a) re-base ADR-002 on SQLite (the researched/recommended path) and let ADR-009's Postgres host only the app relational data, or (b) keep PostgresSaver but add an explicit research/verification line confirming langgraph-checkpoint-postgres maturity + concurrency model on bundled desktop Postgres, and re-justify (or drop) the single-writer lock given Postgres concurrent writes. Brain 2 must force a human decision on which DB owns the checkpoint.

### [deploy-rollback] · **load-bearing**
**Finding:** No rollback/downgrade story exists. Alembic is named for migrations (ARCH §7, ADR-009) but there is zero mention of downgrade() scripts, what happens when a user runs an OLDER app build against a data dir migrated by a NEWER build, or how to recover from a bad migration. Under production-grade posture, deploy/rollback is explicitly a critical concern (CLAUDE_CODE_HANDOFF 'Build Posture' lists 'deploy/rollback' as a critical gap class). REQ-D-101's acceptance signal only covers the forward direction ('older project opens after schema bump'); the reverse (downgrade) is unspecified, and a desktop app shipped to users WILL be downgraded (user reverts a bad update, or restores an old backup).

**Evidence:** ARCHITECTURE_DRAFT.md §7 line 156 ('Alembic migrations; backup = copy folder + pg_dump') and §16; ADR-009 (DECISIONS.md:111) names Alembic but no downgrade path; REQ-D-101 acceptance signal (PRESEARCH.md:313) is forward-only; CLAUDE_CODE_HANDOFF.md lines 11-15 mandate auditing deploy/rollback as critical.

**Proposed fix:** In binding §7/§16 require: (1) every Alembic revision ships a tested downgrade(); (2) a pre-migration automatic DB snapshot (pg_dump or PGDATA copy) taken before any schema upgrade, with a documented restore command; (3) define the supported version-skew policy (e.g. 'app refuses to open a data dir migrated by a newer app version' — see data-dir-version finding) so an accidental downgrade fails safe instead of silently corrupting. Add an acceptance test: migrate up, run, downgrade, reopen with prior app build.

### [deploy-rollback] · **load-bearing**
**Finding:** Data-dir / app-version compatibility is undefined. There is no version stamp written into the data dir, no compatibility check on startup, and no defined behavior when app version and on-disk schema version diverge. The LangGraph checkpointer SHARES the same Postgres (ADR-002/ADR-009), so a schema migration or an interrupted migration can corrupt or orphan IN-FLIGHT pipeline runs — directly colliding with the reconcile-and-resume guarantee (REQ-NF-102, System Flow I). The draft never reconciles 'migrate the DB on app update' with 'resume in-flight runs after reopen': what happens to a checkpoint written by app vN when app vN+1's migration changes the checkpoint tables?

**Evidence:** ADR-002 (DECISIONS.md:41) 'one DB for app data + checkpoints'; ADR-009 (DECISIONS.md:111) 'LangGraph PostgresSaver shares the same DB'; System Flow I (USER_FLOWS.md:112-116) reconcile-and-resume; REQ-NF-102 (PRESEARCH.md:308). No data-dir version stamp or compat gate appears anywhere in ARCHITECTURE_DRAFT.md §7/§16 or DATA_MODEL.md.

**Proposed fix:** Binding ARCHITECTURE must: (1) stamp the data dir with an app-version + schema-revision file and check it at startup, with explicit forward/back policy (open / migrate-with-snapshot / refuse); (2) specify that app updates DRAIN or quiesce in-flight runs before migrating (or that the checkpoint schema is migrated by the same Alembic head that the reconciler reads), and add a test: kill mid-run, update app (run migration), reopen → runs still reconcile or are cleanly marked needs-retry, never silently lost; (3) pin the langgraph-checkpoint-postgres schema version alongside the Alembic head.

### [deploy-rollback] · **load-bearing**
**Finding:** Bundled-Postgres lifecycle and first-run init are essentially unaddressed, and Postgres MAJOR-version upgrades across app updates are a silent deploy landmine. ADR-009 says Postgres is 'bundled + lifecycle-managed (start/health/stop)' and REQ-O-103 covers start/health/restart/stop, but neither covers: first-run cluster creation (initdb), PGDATA location/permissions, the bundled PG binary version pin, OR what happens when an app update ships a new PG major version — PGDATA from PG N is NOT readable by PG N+1 without pg_upgrade. A user updating the app could find their entire local DB (all projects + checkpoints) unopenable.

**Evidence:** ADR-009 (DECISIONS.md:111-113) 'bundled + lifecycle-managed (start/health/stop)' with no initdb/PGDATA/version detail; REQ-O-103 (PRESEARCH.md:317) is start/health/restart/stop only; ARCHITECTURE_DRAFT.md §6.8 (Supervisor) lists 'free-port selection, spawn, /health poll, supervised restart, teardown' — no init/upgrade; §16 line 222 only says 'Local data dir for Postgres + artifacts'.

**Proposed fix:** Binding §6.8/§16 must specify: (1) first-run initdb sequence (create cluster, set locale/encoding, restricted PGDATA perms, localhost/unix-socket-only bind); (2) the pinned PG major version recorded in the data dir; (3) a major-version-upgrade procedure on app update (detect PGDATA version mismatch → pg_dump-with-old-binary then restore-into-new, or bundle pg_upgrade, or refuse-and-instruct) with an automatic backup first. Add a clean-machine first-run smoke test AND a PG-major-bump upgrade test to acceptance.

### [failure-modes] · **load-bearing**
**Finding:** Hang / no-progress detection is missing for both subprocess workers and cloud poll loops — only crashes and timeouts are handled. A Blender process that hangs (stuck import, GPU deadlock, infinite remesh) without crashing, or a cloud job stuck in 'processing'/'in_queue' forever (or a provider that drops a job silently), has no watchdog, max-wall-clock, or max-poll-attempts bound. The architecture lists 'timeouts' generically but never defines a hang/deadline policy, so these stages can wedge a run indefinitely.

**Evidence:** RISKS.md:33 trust-boundary names 'crash/hang' for Blender/@s4tk with mitigation only 'process-tree kill; round-trip validation gate' — no hang DETECTION mechanism. ARCH §6.5 says workers have 'timeouts' but §6.4 provider interface is submit/poll/fetch with no max-poll-budget or stuck-job deadline. RESEARCH.md:24 confirms 'Every viable provider is async submit+poll/webhook' yet no poll-attempt ceiling or stale-job giveup is specified. DECISIONS.md ADR-002 notes 'LangGraph has no watchdog' but the app-owned watchdog covers only startup reconcile, not in-run hangs.

**Proposed fix:** Specify per-stage wall-clock deadlines + a watchdog: cloud poll loop gets max-elapsed + max-attempts → emits PROVIDER_TIMEOUT/stuck-job error and transitions Step→failed (retryable); Blender/@s4tk workers get a hard wall-clock timeout independent of crash detection that triggers process-tree kill → BLENDER_HANG. Add a 'stuck job' sweep (job in running > deadline) to the reconciler/job engine, not just to startup.

But §4 line 80-81 and §9 line 173-174 say the @s4tk worker 'reads donor .package from the user's game install' and 'writes DBPF', and the Blender worker writes preview/normalized-intermediate files — i.e. workers are doing filesystem writes. If workers write into the project artifact tree directly, they are second writers to the filesystem store; if they write to a scratch dir and hand bytes back, the sidecar is sole writer. This is exactly the 'state written by two processes (Python/Node/Blender)' question and it is left implicit.

**Evidence:** ARCHITECTURE_DRAFT.md §4A line 100-102 (worker contracts 'out: cleaned GEOM/preview/report' / 'out: .package + report'), §4 line 80-81, §9 line 173-174 ('@s4tk ... writes DBPF'; Blender writes preview/intermediate); §15 trust boundary (d) 'validate inputs/outputs ... before state writes'.

**Proposed fix:** State the rule in §6.5: workers write only to a sidecar-provided scratch/output directory and return paths; the SIDECAR (repo layer) is the only writer of the canonical artifact tree AND of all Postgres rows after it validates worker output (§15 boundary d). This makes 'sidecar = sole writer' literally true for both stores and resolves the Python/Node/Blender multi-writer question.

**Finding:** CI determinism and offline-eval execution are stated as goals but the mechanism is under-specified and partially self-contradictory with the fail-open/local-first posture. **Proposed fix:** Note startup/reconcile responsiveness as a recordable concern (e.g., async/non-blocking reconcile so the dashboard renders before reconcile completes), or explicitly defer it. No number needed — just name the path and the non-blocking requirement.

### [perf-budgets]
**Finding:** The soft-budget cost path is named (running estimate + warn-before-large-run, REQ-NF-103) and hard caps are correctly deferred, but the cost-ESTIMATION mechanism itself — per-op cost metadata → run rollup → pre-run estimate — is asserted without specifying where the per-op cost figures come from or that they must stay current as models/providers change. This is the data feeding a user-facing gate; if the per-adapter cost metadata is stale or missing, the warn-before-large-run promise silently degrades.

**Evidence:** ARCHITECTURE_DRAFT.md §6.4 ('Cost metadata per op'), §11 ('Cost estimate surfaced; soft-budget warning'); PRESEARCH.md REQ-NF-103 + NFR-budgets (lines 308-326); DATA_MODEL.md Step/Trace carry cost?/latency? fields; A9 (PRESEARCH.md:397).

**Proposed fix:** State in §6.4 that per-adapter cost metadata is part of the provider/model registry config (so it updates with model swaps) and that the run rollup is computed from Step.cost; flag the estimation-accuracy risk as tied to A9. No dollar figures needed.

### [scope-balance]
**Finding:** Minor source-of-truth inconsistency that touches durability scope: DATA_MODEL.md still describes the source of truth as a 'per-project folder on disk; a project DB/JSON index + artifact files', whereas ADR-009 and ARCHITECTURE §7 lock it to app-managed Postgres + files. This is a stale-doc drift, not a scope decision, but it muddies what durability/migration surface (Alembic vs JSON index) is actually in scope.

**Evidence:** DATA_MODEL.md header: 'Source of truth = the local project store (per-project folder on disk; a project DB/JSON index + artifact files).' vs ADR-009 'App-managed local Postgres ... Alembic migrations' and ARCHITECTURE §7 'Source of truth = app-managed Postgres'.

**Proposed fix:** Update DATA_MODEL.md's source-of-truth line to match ADR-009 (Postgres + files), or add a note that 'local project store' = Postgres + artifact files, so the durability/migration scope (Alembic, pg_dump backup) is unambiguous downstream.

### [security-trust]
**Finding:** Subprocess command-validation for the Blender CLI worker is implied but the injection surface is not called out. The Blender worker is invoked as 'blender --background --factory-startup --python <script>' and the @s4tk worker is a Node subprocess; both receive file paths and params that originate from user prompts / provider outputs. The dimension brief lists 'command validation' for the sidecar but the artifacts only mention 'localhost-only bind + command validation' for the IPC layer, never argument/path validation for the spawned subprocesses (a provider-supplied or LLM-supplied filename flowing into a subprocess arg/Blender script).

**Evidence:** ARCHITECTURE_DRAFT §4 (lines 79-81), §6.5 (line 142) describe Blender/@s4tk subprocess workers with 'timeouts, structured errors, process-tree teardown' but no input-arg/path sanitization. RESEARCH R-008 (line 73) notes both CLI & bpy 'install/enable a pinned add-on per run' — another injection path. RISKS.md boundary row 4 (line 33) covers crash/hang/bad-GEOM but not arg/path injection into the subprocess invocation.

**Proposed fix:** State in ARCHITECTURE.md §6.5/§6.8 that subprocess workers receive arguments via argv arrays (never shell string interpolation), all file-path args are resolved/validated under the project artifact root, and the per-run Blender add-on is the vendored pinned one only (no dynamic script path from untrusted input). Low effort, closes the local injection gap.

### [source-of-truth]
**Finding:** Derived/recomputable state is well-bounded but the boundary with authoritative state is not enforced anywhere in the contract. DATA_MODEL line 89-90 cleanly lists status badges, cost/latency estimates, validation rollups, thumbnails, preview composites as 'Derived/display (recomputable), never the source of truth.' Good. But ValidationResult is marked 'derived per run' (line 27) while invariant 1 and FR-VAL-004 make export-blocking decisions FROM validation results — i.e. a derived artifact is load-bearing for a hard gate. If validation results are purely recomputable and not persisted authoritatively, the export gate's auditability (export report must include 'validation summary', PRD §24.2) depends on transient data.

**Evidence:** DATA_MODEL.md line 27 (ValidationResult 'derived per run'), line 89-90 (derived/display list), invariant 1 line 60-61; PRD FR-VAL-004 (line 1439) + §24.2 export report 'Validation summary' (line 1595).

**Proposed fix:** Clarify in ARCHITECTURE.md that ValidationResults used for the export gate are persisted (authoritative snapshot at export time) so the export report and gate decision are reproducible/auditable, distinct from transient validation re-runs in the UI; keep purely cosmetic rollups (badges/thumbnails) as the recomputable class.

### [testing]
**Finding:** EVAL-009 (human-preference harness) and its storage substrate are not fully wired: ADR-008 maps it to LangSmith 'annotation queues' and §7 reserves pgvector 'for preference/similarity (OBS-004/EVAL-009)', but pgvector usage is explicitly 'future' and the local ReviewEvent store (DATA_MODEL) vs LangSmith feedback (ADR-007 'capture user accept/reject as LangSmith feedback/runs') are two parallel sinks with no stated single source of truth or reconciliation. With fail-open tracing, review events captured only to LangSmith could be lost on outage.

**Evidence:** ADR-008 EVAL-009 → 'annotation queues (human-preference)'; ADR-007 'Capture user accept/reject as LangSmith feedback/runs'; §7 'pgvector reserved for preference/similarity (OBS-004/EVAL-009)'; DATA_MODEL ReviewEvent 'append-only authoritative' in local store; REQ-O-102 fail-open means LangSmith may be unreachable.

**Proposed fix:** State in §7/§14 that ReviewEvent in local Postgres is the authoritative source for EVAL-009 (survives LangSmith outage per fail-open), and LangSmith annotation queues are a derived/optional mirror. Confirm whether pgvector preference learning is in-scope for MVP EVAL-009 or deferred; if deferred, say EVAL-009 = capture + export only.
