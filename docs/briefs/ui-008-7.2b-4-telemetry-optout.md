# /tdd brief — telemetry_optout

## Feature
The §18(5) **privacy/telemetry opt-out**: a `persistTelemetryEnabled` settings helper that writes the
`telemetryEnabled` flag over `PUT /settings` (the sidecar reads it to flip its thin-tracing seam). The privacy
**disclosure copy** ("what leaves the machine: provider prompts/images, traces") is **design-fixture (D4), NOT this
slice**.

## Use case + traceability
- **Task ID:** 7.2
- **Architecture sections it implements:** `ARCHITECTURE.md §18` (onboarding prereq #5 — privacy/telemetry
  disclosure + opt-out) + `ARCHITECTURE.md §4` (the `PUT /settings` write of `telemetryEnabled`).
- **Related context:**
  - Contract: `SettingsResponse.telemetryEnabled: boolean` (server-owned — the default lives server-side, so there is
    **no UI-side privacy-default decision**) + `UpdateSettingsRequest.telemetryEnabled?: boolean | null`. Both in
    `generated/contracts.ts`. The endpoint `GET/PUT /settings` is already in the catalog + the client
    (`getSettings`/`updateSettings`, 7.2a).
  - Mirrors `persistModsPath` (`src/settings/settings.ts`, 7.2a) exactly — a one-field partial PUT, no secret on the
    body (rule-5; `UpdateSettingsRequest` has no secret field).
  - **OPEN FINDING (raised to the lead this round):** `PUT /settings` partial-update **merge** semantics are not
    pinned in §4. The UI's mock (`test/fixtures/mock-settings.ts`) implements PATCH-merge (omitted field = unchanged),
    and this slice deliberately mirrors the shipped `persistModsPath` partial-PUT pattern on that assumption. If the
    user resolves the finding to "UI-defensive read-modify-write," this helper **and** `persistModsPath` get
    retrofitted together as a follow-up — out of scope here. Test 2 below makes the merge dependency explicit.

## Acceptance criteria (what "done" means)
- [ ] `persistTelemetryEnabled(client: IpcClient, enabled: boolean): Promise<SettingsResponse>` issues `PUT /settings`
      with a body of **only** `{ telemetryEnabled: enabled }` (partial PUT, mirroring `persistModsPath`), token +
      `Idempotency-Key` (mutating), **no secret on the body** (rule-5), and returns the updated `SettingsResponse`.
- [ ] A subsequent `loadSettings` round-trips the persisted `telemetryEnabled`.
- [ ] Toggling `telemetryEnabled` leaves an already-persisted `simsModsPath` intact (the merge assumption — see the
      open finding; test 2).
- [ ] All unit tests in `test/settings/settings.test.ts` pass.
- [ ] `/preflight` clean.
- [ ] No cross-doc invariant change (consume-only).

## RED test outline (Step 2)
`test/settings/settings.test.ts`:
1. **`test_persist_telemetry_enabled_puts_and_round_trips`** — `persistTelemetryEnabled(client, true)` PUTs
   `telemetryEnabled:true`; a subsequent `loadSettings` returns `true`.
   - Asserts: returned + reread `telemetryEnabled === true`; the PUT carried the token. Why: `§4`/`§18` round-trip.
2. **`test_persist_telemetry_only_sets_telemetry_and_preserves_mods_path`** — starting from
   `{simsModsPath:"/m/Mods", telemetryEnabled:true}`, `persistTelemetryEnabled(client, false)` sends a body of ONLY
   `{telemetryEnabled:false}` and (under merge) leaves `simsModsPath` intact.
   - Asserts: PUT body keys === `["telemetryEnabled"]`; reread `simsModsPath === "/m/Mods"` AND `telemetryEnabled ===
     false`. Why: pins the partial-PUT pattern + makes the merge dependency explicit (open finding).
3. **`test_persist_telemetry_never_carries_a_secret`** — body keys ⊆ `{simsModsPath, telemetryEnabled}`, none
   matching `/key|secret|token|password|credential/i`.
   - Asserts: no secret field on the body. Why: rule-5 (secrets are keychain-only, never on the settings body).
4. **`test_persist_telemetry_put_carries_idempotency_key`** — the mutating PUT carries both token + `Idempotency-Key`.
   - Asserts: both headers present. Why: `§4` R9 (may be partly covered by the existing generic settings test; keep a
     telemetry-specific assertion).

## Things to flag at Step 2.5
1. **Partial PUT vs read-modify-write.** My default vote: **partial PUT** (mirror the shipped `persistModsPath`;
   consistent + the open finding tracks the contract pin). Do NOT pre-emptively switch to read-modify-write here — if
   the user resolves the finding that way, both helpers change together as a follow-up.
2. **Naming / polarity.** `persistTelemetryEnabled(client, enabled)` matching the contract field, vs a
   `setTracingOptOut(optedOut)` framing. My default vote: **`persistTelemetryEnabled(enabled)`** — match the contract
   field directly; the "opt-out" UX (enabled=false ⇒ opted out) is the disclosure screen's framing, kept out of the
   data helper to avoid polarity bugs.
3. **Initial toggle state.** Reuse `loadSettings().telemetryEnabled` (no new read helper). My default vote: **reuse
   `loadSettings`**.
4. **Disclosure copy.** Confirm the "what leaves the machine" disclosure text + the toggle control are
   **design-fixture (D4)**, not `/tdd`. My default vote: **design-fixture** (visual/copy, not deterministic logic).
